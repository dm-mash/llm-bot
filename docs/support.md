# Ассистент поддержки

Мини-сервис, который отвечает пользователю по продукту «Учёт», опираясь на его
собственное обращение. Ответ строится из двух источников, и нужны оба:

- **RAG** — база знаний продукта (`faq/faq.md`): как продукт устроен и какая
  процедура положена по умолчанию;
- **MCP** — стол поддержки с клиентами и их тикетами: что происходит именно с
  этим клиентом.

Одной половины мало. FAQ знает, что ссылка сброса пароля живёт 30 минут; тикет
знает, что этот конкретный клиент уже третий день не получает писем и общая
инструкция «проверьте спам» ему уже давали.

## Подготовка

```bash
cp support.example.json data/support.json     # демо-стол: 3 клиента, 5 тикетов
cp mcp.example.yaml data/mcp.yaml             # там уже описан сервер support
cp agents.example.yaml data/agents.yaml       # там уже описан агент support
```

Индекс базы знаний:

```bash
.venv/bin/python scripts/index_documents.py --input_dir faq \
  --extensions .md --strategy structure --index_dir data/faq_emb --out ""
```

## Запуск

```bash
SERVE_TOKEN=secret .venv/bin/python scripts/serve_llm.py \
  --agent support \
  --rag-index data/faq_emb/index_structure.json \
  --support
```

Токен достаточно задать переменной окружения: `--token` по умолчанию читает
`$SERVE_TOKEN`, поэтому дублировать его флагом не нужно. А вот конструкция
`SERVE_TOKEN=secret ... --token "$SERVE_TOKEN"` не работает — оболочка
раскрывает `"$SERVE_TOKEN"` в аргументах раньше, чем префиксное присваивание
попадёт в окружение процесса, и `--token` получит пустую строку (сервер
запустится без авторизации и скажет об этом в строке `Listen ...`).

Агент — один и тот же: сервер, запущенный под поддержку, отвечает и на `/support`,
и на странице чата **одним и тем же** агентом, заданным в `--agent`. Поэтому
`--agent` здесь указывает на агента, написанного под поддержку (`support` в
`agents.example.yaml`), а не на универсального помощника.

`--support` — единственный флаг поддержки: он включает фичу целиком (эндпоинт
`/support`, список `/support/tickets`, выпадашка и инструменты на странице чата).
Без него маршрутов `/support*` на сервере нет вовсе: они не регистрируются и не
появляются в `/openapi.json`, а не отвечают 404 на каждый запрос.

Отдельных `--support-rag-index`, `--support-top-k`, `--support-rerank`,
`--support-mcp` нет намеренно: FAQ лежит в том же корпусе, что и документация
для чата, поэтому `/support` использует общие `--rag-index`, `--rag-top-k`,
`--rag-rerank` и `--mcp-config`. Это же означает, что эмбеддер грузится один раз
на процесс, а не два. Обратная сторона: если чат запущен без `--rag-index`,
то и у `/support` RAG выключен — молча отвечать из индекса, который никто не
выбирал, ассистент не станет.

Сервер стола поддержки должен называться в `data/mcp.yaml` так же, как в
`mcp.example.yaml`, — `support`. Если его нет в конфиге, `/support` продолжает
работать: отвечает по FAQ, но без данных тикета, о чём пишет предупреждение при
старте (эндпоинт чата при этом не страдает).

Переменная окружения: `SERVE_SUPPORT` (любое непустое значение, кроме `0`, `false`, `no`, включает).

## Запрос

```bash
curl -s http://localhost:8000/support \
  -H "Authorization: Bearer secret" -H "Content-Type: application/json" \
  -d '{"question": "Почему не работает авторизация?", "ticket_id": "T-5001"}'
```

Поля: `question` (обязательно), `ticket_id`, `user_id`, `session_id`. Без
идентификаторов ассистент отвечает на общий вопрос о продукте, а не по
конкретному обращению.

Ответ:

```json
{
  "answer": "Письма со сбросом не доходят …",
  "sources": ["faq.md:12-18"],
  "tools": ["support__get_ticket"],
  "grounding": "grounded",
  "usage": {"prompt_tokens": 900, "completion_tokens": 180, "total_tokens": 1080},
  "session_id": "support-6f1c0a2b9d34"
}
```

`sources` — откуда взят ответ, `tools` — какие инструменты поддержки реально
вызвались, `grounding` — подтверждено ли утверждение источником. Пустой `sources`
означает, что ответ пришёл из памяти модели, а не из базы знаний.

### Почему у FAQ отдельный корпус

FAQ лежит в `faq/`, а не рядом с документами кофейни в `knowledge_base/`, и
индекс у него свой (`data/faq_emb`). Пока они были одним корпусом, на вопрос
«Почему не работает авторизация?» в выдаче оказывался кусок про зёрна:
эмбеддинг не знает про границы каталогов и мешает всё, что лежит рядом.

Каталог `faq/` добавлен в исключения индексера, поэтому он не попадает и в
корпус документов репозитория — тот же случай, что и `knowledge_base/`.

## Разговоры

`session_id` задаётся в теле или заголовке `X-Session-Id`. Если его нет,
каждый запрос получает **свой** разговор: стол поддержки обслуживает многих
клиентов сразу, и общий диалог на всех означал бы, что один клиент увидит
тикет другого. Продолжить разговор — значит передать тот же `session_id`.

## Инструменты поддержки (MCP)

Сервер `llm_bot/mcp_servers/support.py`, четыре инструмента, все только на чтение:

| Инструмент | Что делает |
|---|---|
| `get_ticket(ticket_id)` | тикет с перепиской и данными клиента |
| `get_user(user_id)` | карточка клиента: тариф, статус |
| `list_tickets(user_id, status)` | тикеты клиента, новые сверху |
| `search_tickets(query)` | поиск по теме, тегам и тексту переписки |

Инструмента, который что-то меняет, нет намеренно: ассистент, который
отвечает на вопросы о столе поддержки, не должен иметь права его менять.

Файл стола берётся из `SUPPORT_DB` (по умолчанию `data/support.json`).

## Выбор обращения в чате

На странице чата (`GET /`) появляется выпадашка «Обращение» — её наполняет
`GET /support/tickets`. Панели не видно, пока сервер не отдал список: на сервере
без стола поддержки эндпоинта нет, и пустой список только шумит.

Выбранный тикет едет **заголовком** `X-Ticket-Id`, а не попадает в текст
вопроса: сервер превращает его во временную директиву для этого хода, и ассистент
сам открывает обращение инструментом `get_ticket`. Поэтому

- в истории диалога остаётся только сам вопрос — переключение тикета не оставляет
  в контексте предыдущего обращения;
- ассистент работает с тем, что инструмент вернул сейчас, а не с копией, которую
  сервер мог устареть.

Заголовок можно поставить и вручную:

```bash
curl -s http://localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer secret" -H "Content-Type: application/json" \
  -H "X-Ticket-Id: T-5002" \
  -d '{"messages":[{"role":"user","content":"Клиент потерял телефон, что делать?"}]}'
```

Чтобы тикет вообще открылся, чат-эндпоинту нужны инструменты поддержки — они
подключаются автоматически, когда задан `--support` и сервер `support`
есть в `data/mcp.yaml`. Без стола поддержки заголовок примут, но читать будет
нечего.

## Ошибки

| Код | Когда |
|---|---|
| 400 | пустой `question`, неверный JSON, отказ инвариантов |
| 401 | нет или неверный bearer-токен |
| 413 | переполнение контекста диалога |
| 429 | превышен лимит запросов |
| 502 | модель недоступна (503/504 — очередь и таймаут) |
| 503 | сервер занят |
