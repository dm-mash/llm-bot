# Управление контекстом: стратегии (без summary)

## Цель

Реализовать в агенте три разные стратегии управления контекстом **без summary**
и переключатель между ними, затем протестировать на едином сценарии
(«собираем ТЗ», 10–15 сообщений) и сравнить качество, стабильность, расход токенов
и удобство.

Стратегии (фокус задачи):

1. **Sliding Window** — в запрос идут только последние N сообщений.
2. **Sticky Facts / Key-Value Memory** — блок `facts` (ключ-значение),
   обновляемый после каждого сообщения; в запрос идут `facts` + последние N.
3. **Branching** — автоматические checkpoints при ветвлении, 2+ ветки от одной
   точки, независимое продолжение, переключение между ветками.

## Ключевые решения

### A. Существующая суммаризация — тоже одна из стратегий

Вводим единый интерфейс `ContextStrategy`, через который реализуются ВСЕ способы
управления контекстом. Переключатель — один и общий.

| Ключ        | Стратегия                  | Описание                                    | Summary? |
|-------------|----------------------------|---------------------------------------------|----------|
| `full`      | (отсутствует)              | Полная история, ничего не урезаем (по умолч.)| нет      |
| `summary`   | Rolling-summary            | Существующий [`ContextCompressor`](llm_bot/compress.py:154) | **да** |
| `sliding`   | Sliding Window             | В запрос — только последние N               | нет      |
| `facts`     | Sticky Facts / KV-память   | `facts` + последние N                       | нет      |
| `branching` | Branching                  | Авто-checkpoints + ветки                    | нет      |

Агенты, настроенные через `keep_last_messages` / `summarize_messages_threshold`,
по-прежнему работают как стратегия `summary` (обратная совместимость). Если
стратегия не задана — поведение `full` (как сейчас). Три новые стратегии
(`sliding`, `facts`, `branching`) реализуются **без** summary.

### B. «Отбрасывать» = не отправлять в запрос, НЕ удалять из хранилища

Стратегия формирует только **request-стек** (что поедет в модель). Полная история
остаётся на диске (через `SessionStore`) — чтобы её можно было возобновить,
проанализировать или использовать для ветвления. Ничего не теряется безвозвратно.

Разделение ответственности:
- `SessionStore` хранит **полную** историю.
- `ContextStrategy.prepare(history, user_msg)` возвращает, **какую часть** этой
  истории и какой доп. контекст (`facts`/summary) отправить модели.

### C. Branching: checkpoint создаётся автоматически при ветвлении

Ручной команды `/checkpoint` нет. `/branch <name>` **сама фиксирует точку форка**
(текущую позицию в активной ветке) и создаёт новую ветку от неё. Каждая ветка
держит собственную полную историю.

## Текущая архитектура (контекст)

- [`Session`](llm_bot/agent.py) — владелец диалога: `_history`, опционально
  `_compressor` (rolling-summary) и `_summary`.
- [`Agent.build_messages()`](llm_bot/agent.py) собирает стек сообщений:
  `[summary?] + [system] + history`.
- [`ContextCompressor`](llm_bot/compress.py) — единственная существующая стратегия.
- Сравнительные эксперименты (см. [`scripts/compare_compression.py`](scripts/compare_compression.py))
  построены на фейковой детерминированной LLM через `httpx.MockTransport`.

## Дизайн

### Абстракция `ContextStrategy`

Новый модуль `llm_bot/context_strategies.py`.

```python
@dataclass
class PreparedTurn:
    request_history: list[dict]  # часть полной истории, уходящая в запрос
    prefix: list[dict]           # доп. контекст перед системным промптом
                                 # (facts-блок / summary)
    dropped: int                 # сколько сообщений исключено из запроса
    event: ContextEvent | None   # событие для UX/диагностики

class ContextStrategy(ABC):
    name: str
    def prepare(self, history, user_msg) -> PreparedTurn: ...
    def after_reply(self, user_msg, reply) -> None: ...     # обновить долговр. состояние
    def load_state(self, store, session_id) -> None: ...
    def save_state(self, store, session_id) -> None: ...
```

`Session.chat_with_details` делегирует стратегии формирование request-стека и
обновление долговременного состояния. Реестр `name -> фабрика` позволяет
выбирать стратегию строкой (конфиг/CLI).

`Agent.build_messages` расширяется: принимает `prefix` (facts/summary) и
`request_history`. Полная история не усекается — Session по-прежнему дописывает
`user`/`assistant` сообщения в полную историю и сохраняет её целиком.

Существующий rolling-summary адаптируется под этот интерфейс как стратегия
`summary` (обёртка над `ContextCompressor`), не ломая текущие тесты.

### Стратегия `sliding`: SlidingWindow

- Параметр: `window_size: int` (N).
- `prepare`: `request_history = history[-N:]` (последние N), `prefix=[]`,
  `dropped = len(history) - N`.
- Полная история сохраняется в хранилище; в модель идёт только окно.
- Без долговременного состояния, `after_reply` — no-op.
- Плюс: дёшево, предсказуемо. Минус: при малом N модель не видит ранние детали ТЗ.

### Стратегия `facts`: StickyFacts

- Параметры: `window_size: int` (N), `max_facts: int`.
- Состояние: `facts: dict[str, str]` (ключ-значение).
- `prepare`: `request_history = history[-N:]` + `prefix`-сообщение
  `[system] "Известные факты: ..."` из `facts`. Отправляется `facts` + последние N.
- `after_reply`: отдельный LLM-вызов (как суммаризация), читающий весь ход
  (`user` + `reply` + текущие `facts`) и возвращающий обновлённый `facts`.
  Ключи — тип факта (цель, ограничения, предпочтения, решения, договорённости).
- Расход: +1 LLM-вызов на ход на обновление фактов — биллится отдельно.

### Стратегия `branching`: Branching

- Состояние: `branches: dict[id -> полная история]`, `current: id`.
- `/branch <name>` — авто-checkpoint текущей позиции, создаёт ветку с историей
  до точки форка включительно, переключается на неё.
- `/switch <name>` — переключиться на существующую ветку.
- `/branches` — список веток (имя + длина).
- `prepare`: `request_history` = история текущей ветки (обрезана до N, если задан
  `window_size`), `prefix=[]`.
- `after_reply`: дописывает ответ в полную историю текущей ветки.
- Плюс: исследование альтернатив без потери исходного пути.
  Минус: больше состояний, ручное переключение.

### Конфигурация и CLI

- В `AgentConfig` добавить поле `context_strategy` (+ параметры каждой стратегии:
  `window_size`, `max_facts` и т.п.).
- В `factory.make_session` строить стратегию из конфига агента (реестр по имени).
- В CLI добавить `--strategy {sliding,facts,branching}` для переопределения и
  slash-команды для branching (`/branch`, `/switch`, `/branches`).

### Персистентность

`JsonSessionStore` расширить: кроме `summary`/`history` хранить
`facts`, `branches`, `current_branch`. Новые ключи опциональны — формат обратно
совместим. Полная история всегда сохраняется.

### Тесты и сравнение

- Юнит-тесты: `tests/test_context_strategies.py` — поведение каждой стратегии
  (формирование request-стека, обновление facts, ветвление/переключение) на
  `httpx.MockTransport`; проверка, что полная история не теряется в хранилище.
- Сценарий «ТЗ»: 12–14 сообщений, каждый ход добавляет факт ТЗ
  (имя проекта, цель, срок, бюджет, ограничения, стек, участники, ...).
  Финальный recall-вопрос «перечисли все требования из разговора».
- Фейковая LLM отвечает на recall тем, что видит в **request-стеке** — честно
  моделирует «что стратегия реально передала модели».
- Скрипт `scripts/compare_context_strategies.py` прогоняет один сценарий на каждой
  стратегии, считает recall-качество, промпт-токены, токены обновления фактов,
  число исключённых из запроса сообщений; пишет
  `results/context_strategies_analysis.md`.

### Метрики сравнения

- **Качество**: recall (доля фактов ТЗ, видимых модели в финальном request-стеке).
- **Стабильность**: не теряются ли ранние/ключевые детали (какие факты не попали
  в запрос у каждой стратегии).
- **Расход токенов**: суммарные промпт-токены основных ходов + затраты на
  обновление facts (для `facts`) и на суммаризацию (для `summary`).
- **Удобство**: автономность (sliding/facts) vs ручное управление (branching),
  сложность использования.
