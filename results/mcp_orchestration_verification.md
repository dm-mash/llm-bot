# Проверка: оркестрация MCP — длинный флоу через несколько серверов

Дата: 2026-09-28 · Тесты: **424 passed** (весь набор, `pytest -q`), из них
**8 новых** в [`tests/test_mcp_orchestration.py`](../tests/test_mcp_orchestration.py):
длинный кросс-серверный флоу, кросс-серверный батч, граница бюджета раундов,
прокладка конфига (`max_rounds` + `MCP_CONFIG`) и четыре регрессии живых
находок (две битые формы директив + выдуманный результат инструмента с
границей бюджета). Контрольный живой CLI-прогон сокращённой цепочки
(currency_yahoo + notes) прошёл до конца — см. «Находки живого прогона», п. 1в–1г.

## Требования ТЗ → реализация

| Требование | Реализация | Проверка |
|---|---|---|
| Зарегистрированы несколько MCP-серверов | `notes`, `scheduler`, `currency_yahoo` в одном конфиге; в демо — 14 инструментов от трёх серверов в одном блоке промпта | e2e: `router.tools` содержит все три неймспейса |
| Агент выбирает нужный инструмент | промпт-протокол в [`render_tools_block`](../llm_bot/mcp_tools.py) (контракты данных в первых строках docstring + инструкция «строй ЦЕПОЧКУ… ПО ОДНОМУ») | scripted: из одного промпта модель сама собирает пайплайн из 5 вызовов |
| Корректная маршрутизация | неймспейсинг `server__tool`, роутинг по владельцу в [`MCPRouter.call_tool`](../llm_bot/mcp_tools.py), изоляция сбоев | e2e: каждый вызов прилетел своему серверу (`event.server`), 3 сервера в одном флоу |
| Длинный флоу взаимодействия | цикл агента с бюджетом раундов; бюджет настраивается ключом `max_rounds` в `mcp.yaml` (дефолт 4 не влезал) | scripted: 5 вызовов / 6 раундов LLM при `max_rounds: 8`; при `max_rounds: 2` — ровно 2 вызова, чистая остановка |
| Сценарий с инструментами разных серверов | «проанализируй курс USD за 2025, сохрани отчёт, добавь заметку с итогом и поставь ежедневный сбор на 09:00» → `currency_yahoo` ×3 → `notes` → `scheduler` | e2e + живой детерминированный прогон (демо) |
| Корректность выбора и порядка вызовов | ассерты точного порядка `[(server, tool, ok)]`; побочные эффекты во всех трёх хранилищах | e2e: порядок fetch → analyze → save_report → add_note → schedule_task; отчёт/заметка/задача на диске |

## Флоу под тестом

```
пользователь
   └─> Session (цикл агента, бюджет max_rounds из конфига)
         └─> MCPRouter (единый блок инструментов, server__tool)
               1. currency_yahoo__fetch_rates    → ряд точек (JSON)
               2. currency_yahoo__analyze_rates  ← ряд №1 → агрегаты
               3. currency_yahoo__save_report    ← агрегаты №2 → id отчёта
               4. notes__add_note                ← числа из №2 в тексте → id заметки
               5. scheduler__schedule_task       ← mcp_call(fetch_rates) ежедневно 09:00
         <─ служебные ответы с результатами каждого шага
   └─> финальный ответ пользователю
```

## Три уровня проверки

1. **Scripted-LLM e2e** ([`tests/test_mcp_orchestration.py`](../tests/test_mcp_orchestration.py))
   — LLM зашит на HTTP-слое, MCP-сторона реальная: все три сервера живут как
   stdio-процессы, currency — офлайн (`CURRENCY_FIXTURE`). Проверено:
   - точный порядок и адресация пяти вызовов; `len(payloads) == 6`;
   - передача данных между серверами: агрегаты анализа байт-в-байт дошли до
     модели служебным сообщением, текст заметки содержит именно эти числа
     (100.0 → 102.5, +2.5 %, рост), задача планировщика несёт
     `payload.server=currency_yahoo, tool=fetch_rates`;
   - побочные эффекты: `reports.json` (end_rate 102.5), `notes.json`
     (id=1, теги), `scheduler.json` (`daily 09:00`, активна);
   - батч-директива смешивает серверы в ОДНОМ раунде (2 LLM-запроса);
   - граница бюджета: `max_rounds=2` при скрипте из 3 вызовов → ровно 2
     вызова по порядку, третий не выполняется (стор планировщика даже не
     создаётся), «хвостовая» директива остаётся финальным ответом —
     задокументированный граничный контракт;
   - прокладка конфига: `max_rounds` течёт `YAML → MCPRouter.max_rounds →
     Session`; `MCP_CONFIG` перенаправляет поиск конфига (в т.ч. ошибку
     «конфиг не найден» — громкую, не молчаливую).

2. **Детерминированная кросс-серверная цепочка на живых данных**
   ([`scripts/mcp_orchestration_demo.py`](../scripts/mcp_orchestration_demo.py),
   лог: [`results/mcp_orchestration_demo.md`](mcp_orchestration_demo.md)) —
   Yahoo, USD за 2025: 24 точки, **113.7222 → 79.4962 (−30.1 %, падение)**,
   min 77.7971 (2025-07-10). Пять вызовов `server__tool` через роутер —
   **5×OK**: отчёт `id=00d50877`, заметка `id=1` (теги «валюта, отчёт»),
   задача-сборщик создана (`mcp_call`, ежедневно 09:00, группа «финансы»).
   Это доказывает сквозную передачу данных сервер → сервер без LLM.

3. **Живой агент** — CLI-прогон сокращённой цепочки (2 сервера, 4 вызова)
   прошёл до конца: отчёт и заметка сохранены, финальный ответ — чистый
   текст (п. 1в). Полный 5-вызовный флоу упирается в квоту провайдера
   (п. 2); механика полностью покрыта пунктами 1–2.

## Что добавлено в инфраструктуру

- **`max_rounds`** — верхнеуровневый ключ `mcp.yaml` (рядом с `servers:`):
  бюджет раундов tool-цикла. Течение: YAML →
  [`MCPRouter.max_rounds`](../llm_bot/mcp_tools.py) → сессия (явный
  `Session(mcp_max_rounds=...)` по-прежнему главнее). Дефолт — 4, как раньше.
- **`MCP_CONFIG`** — env-override расположения конфига
  ([`_config_path`](../llm_bot/mcp_tools.py)). Нужен, потому что
  creation-time валидация `mcp_call` в планировщике читает конфиг в СВОЁМ
  процессе: теперь CLI, scheduler-сервер и демо указывают на один и тот же
  файл без хардкода `data/mcp.yaml` — тесты и демо самодостаточны во
  временных путях.
- **Парсер директив стал устойчивым** ([`parse_directives`](../llm_bot/mcp_tools.py)):
  ищет первый ВАЛИДНЫЙ JSON-объект с `call_tool` через
  `json.JSONDecoder.raw_decode` вместо среза «от первого `{` до последнего
  `}`».
- **Защита от выдуманного результата инструмента**
  ([`agent.py`](../llm_bot/agent.py)): если модель вместо директивы
  вернула самодельную строку «Результат инструмента …», цикл распознаёт
  подделку служебного формата, вставляет корректирующий ход и даёт
  переделать шаг в пределах бюджета `max_rounds`.

## Находки живого прогона

1. **Реальные сбои директивного протокола от живой модели** (все закрыты).

   **а. План перед директивой.** Модель `openai/gpt-oss-120b` приписала к
   директиве план действий с фигурными скобками (`payload
   {"currency_code":"USD"}`, …`). Старый парсер брал срез от первого `{` до
   последнего `}` — получал битый JSON и молча терял директиву (0 вызовов).
   Новый — находит первый валидный JSON-объект с `call_tool`
   (`raw_decode`-скан); регрессия:
   `test_parser_survives_planning_text_before_directive`.

   **б. Несбалансированный JSON директивы.** В живом CLI-прогоне
   («проанализируй курс доллара за 2026 год и сохрани отчёт в заметки»,
   `--mcp currency_yahoo,notes`) модель во втором раунде выдала
   `{"call_tool": {...}}]` — потерянная закрывающая скобка внешнего объекта
   плюс лишняя `]`. Парсер возвращал `[]` → цепочка вставала, а сырая
   директива уходила пользователю как финальный ответ. Добавлен
   best-effort ремонт скобок (`_close_unbalanced_brackets`: лишние
   закрывающие отбрасываются, незакрытые добираются) — только как fallback,
   когда обычный парсинг не сработал, но в тексте есть `call_tool`;
   корректные ответы проходят как раньше. Регрессия:
   `test_parser_repairs_unbalanced_directive_json`.

   Отдельно: в том же прогоне модель вернула **пустой `content`**, а
   директиву — в поле `reasoning`; клиента это спасло штатным фолбэком
   (reasoning-текст попадает в ответ), после чего парсер нашёл директиву —
   первый вызов цепочки выполнился без изменений кода.

   **в. Контрольный прогон после обоих фиксов.** Повтор той же команды
   (`--mcp currency_yahoo,notes`) прошёл целиком: `fetch_rates` →
   `analyze_rates` → `save_report` (id=35f81fd7, «Анализ курса USD/RUB за
   2026 год») → `notes__add_note` (id=7, теги
   analysis/usd/2026/report) → чистый текстовый ответ с числами анализа —
   сырой JSON пользователю больше не утекает. Формы ответов модели:
   р1 — директива в чистом `content`; р2 — снова пустой `content`, а
   директива — в конце `reasoning` ПОСЛЕ плана с фигурными скобками
   (спасли reasoning-фолбэк и `raw_decode`-скан из п. 1а); р3–р4 —
   чистые `content`-директивы с корректными аргументами (агрегаты анализа
   переданы без изменений, id отчёта из р3 подставлен в текст заметки).
   Несбалансированная форма из п. 1б в этом прогоне не повторилась
   (стохастично) — её путь закрыт регрессией на точной битой строке
   из живого лога.

   **г. Выдуманный результат инструмента.** В другом живом прогоне (та же
   команда, «сохрани текстовую форму отчёта в заметки») модель во втором
   раунде НЕ вернула директиву: настоящий вызов `analyze_rates` со всем
   рядом точек (24 значения) остался в недоступном парсеру поле
   `reasoning`, а в
   `content` ушла СФАБРИКОВАННАЯ строка «Результат инструмента
   currency_yahoo__analyze_rates: {…}» с выдуманной схемой агрегатов.
   Цикл не увидел директивы и отдал подделку пользователю как финальный
   ответ — шаг был пропущен. Закрыто двумя мерами: (1) цикл в
   [`agent.py`](../llm_bot/agent.py) распознаёт самозванство под
   служебный формат (`_looks_like_fabricated_feedback`) и, пока позволяет
   бюджет раундов, вставляет корректирующий служебный ход — модель
   переделывает шаг, и инструмент вызывается ПО-НАСТОЯЩЕМУ; на границе
   бюджета ответ проходит как есть (та же документированная граница, что
   у «хвостовой» директивы); (2) в блок инструментов
   ([`render_tools_block`](../llm_bot/mcp_tools.py)) добавлена явная
   инструкция «служебные сообщения пишет ТОЛЬКО система». Регрессии:
   `test_fabricated_tool_result_gets_corrected`,
   `test_fabricated_reply_at_budget_edge_is_delivered`.
2. **Квота провайдера (Groq free tier, 8000 TPM)**: запрос с блоком из 14
   инструментов стоит ~1–3k токенов и растёт с каждым раундом (контекст
   копит результаты инструментов). В первом прогоне полного 6-раундового
   флоу провайдер отвергал запросы при частично израсходованном окне:
   `Used 4650 + Requested 3595 > 8000` → 429 после 4 ретраев. Сокращённая
   цепочка (2 сервера, 5 LLM-раундов) помещается: максимум 3020 токенов
   за запрос, два transient-429 поглощены штатными ретраями клиента,
   помогает и провайдерский кэш промпта (`cached_tokens: 1536`).
   Ограничение тарифа, не протокола: при квоте выше или локальной модели
   полный флоу проходит без изменений кода (механика доказана
   scripted-тестами и детерминированным прогоном).
3. **Стохастичность протокольного поведения модели**: в разных прогонах
   одна и та же модель то выдавала корректную директиву (пусть и с планом
   впереди — см. п.1), то отвечала нативной tool-call разметкой, от которой
   провайдер оставляет обрывок «(Waiting for tool response)». Это тот же
   класс ограничений, что задокументирован в
   [`mcp_currency_yahoo_verification.md`](mcp_currency_yahoo_verification.md):
   для моделей, обученных нативному tool-calling, нужен транспорт с
   параметром `tools` — вне рамок проекта (плоские chat-completions).

## Итог

Требования задачи выполнены: несколько серверов зарегистрированы и
рекламируются одним блоком; агент выбирает инструменты по контрактам;
маршрутизация проверена по `server`-атрибуции каждого события; длинный
кросс-серверный флоу (5 вызовов, 3 сервера, 6 раундов) проходит
автоматически с точным порядком и передачей данных между серверами,
бюджет раундов настраивается в конфиге, а насыщенность сценария
подтверждена живым детерминированным прогоном, scripted-тестами и живым
CLI-прогоном сокращённой цепочки.

Кросс-провайдерская проверка: тот же сценарий проходит и через
`labs-leanstral-1-5` (Mistral, агент `leanstral`) без единой правки кода —
4 директивных раунда + финал, каждый запрос с первой попытки (HTTP 200
без ретраев), нативные `tool_calls` не задействованы: модель следует
промпт-протоколу в чистом `content`. Побочные эффекты: отчёт
id=02a0f0b4, заметка id=8; финальный ответ — структурированный текст с
реальными числами анализа. Протокол не завязан на конкретного
провайдера.
